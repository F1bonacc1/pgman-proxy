TL 1 · 0/16B3748

Highly available PostgreSQL, with no external coordinator, VIP or Kubernetes

Each node runs one binary. It holds a TCP proxy, an operator API, an embedded NATS server and the pg-manager engine, and it drives the local Postgres. Any peer accepts connections. One Postgres takes writes.

Where to go next

A thin scaffold around an engine

pg-manager is a Go library that decides. pgman-proxy is the binary that gives it a network, a config and an API. New HA behaviour lands in the library first, and a CI grep gate rejects engine commands in proxy source.

The reconciler: one loop per node

Every decision passes through a pure function. It takes a state and an event and returns the next state, with no I/O. That is why it can be property-tested for "at most one primary".

Node state machine

Pick a story to trace it. The transitions come from state/transitions.go. Failed and Fenced are sticky: only an operator (or a proven-safe recovery gate) leaves them.

What is plugged in

The engine imports no NATS and no Kubernetes. It talks to interfaces; the host chooses the implementations. This is what pgman-proxy injects.

Shared state: one KV bucket per cluster

Everything nodes must agree on lives in the JetStream bucket pgmgr_<cluster>, replicated to 3 servers. Keys below are under pgmgr/<cluster>/, except leader.

Boot gates and drain order

Each boot gate has its own exit code, so a supervisor can tell what failed. The drain order is what makes a stopped primary lose nothing: Postgres stops before the lease is released.

        One node, every socket

        pgmctl: a client, never a peer

        It never embeds NATS and never opens a Postgres connection. It only uses the /v1/* API.

        Control-plane API

        Any peer accepts any call. Leader-only calls are forwarded over NATS (or redirected with a 307). Every mutating call is audited, and an audit failure rejects the call.
